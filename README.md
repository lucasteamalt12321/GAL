# GAL — Global Achievement List

Глобальная платформа рейтинга человеческих достижений. Достижения из разных сфер сравниваются через единую относительную шкалу сложности, построенную на личных сравнениях пользователей.

Идея и исследовательская рамка проекта (модель Bradley–Terry, попарные сравнения, задачи, новизна) — [docs/idea.md](docs/idea.md).

## Что умеет

- регистрация, вход (включая **вход через LTHub**), выход, восстановление пароля и смена пароля;
- предложение достижения с доказательством собственного выполнения (файл или ссылка);
- редактирование и удаление своего достижения, пока оно на модерации;
- модерация достижений и proofs, скрытие опубликованных достижений, история решений;
- личная шкала сложности: при создании — «Ожидаемая сложность», при прохождении — «Сложность»; выбор через сравнения «сложнее/легче», без номеров топ-1/2/3;
- глобальный рейтинг достижений по модели **Bradley–Terry** (каждое попарное сравнение из личных шкал — отдельное соревнование; BT-рейтинг, число сравнений, ± SE и 95% доверительный интервал), очки игроков относительно лучшего BT-рейтинга (максимум 1000, каждые 400 пунктов разницы уменьшают награду в 10 раз; только постоянные ranked-достижения) и топ игроков;
- предварительный **топ-5**: при прохождении достижения пользователь отмечает «заявка в топ-5» (место 1–5 + обоснование сложности); модератор в общей очереди выбирает «принять как сложное» (со своим местом 1–6), «принять» или «отказать»; одобренное достижение получает временную позицию `#3*` в общем топе и становится постоянным после третьей обычной оценки;
- при отправке прохождения можно **скрыть доказательство** от других пользователей; скрытые доказательства не показываются в публичных списках, но остаются видны владельцу и модераторам. Верификацию создателя скрыть нельзя;
- публичные страницы: профиль игрока (очки, пройденные и созданные достижения) и карточка достижения (место, BT-сила, прошедшие пользователи, отправка прохождения);
- жалобы на достижения и их рассмотрение;
- «Мои заявки»: все заявки в одной вкладке — о выполнении и в топ-5; у подтверждённых, но не оценённых выполнений есть кнопка «Оценить сложность»; на странице оценки показываются такие достижения как напоминание;
- профили, настройки профиля, пагинация и поиск по каталогу;
- технический запрет абсолютно идентичных заявок: БД считает отпечаток нормализованного содержимого, хранит историю попыток и блокирует точный повтор; прохождение и заявка в топ-5 из одной формы — разные заявки;
- эксперимент по точности/устойчивости рейтинга (`scripts/bt_experiment.py`).

## Стек

- **Backend:** Python 3.12, FastAPI, Jinja2

## Вход через LTHub

GAL — публичный OAuth-клиент LTHub (authorization code + PKCE, без client secret). Кнопка есть на страницах входа и регистрации; при первом входе создаётся Supabase-аккаунт с **ником из LTHub** (если он свободен; иначе добавляется суффикс), привязанный к LTHub-профилю в `external_identities`. Подробности протокола — в `core/oauth.py` LTHub и `app/routers/lthub_auth.py`.

**Пароль LTHub-аккаунта — это пароль в LTHub.** GAL не заводит для таких аккаунтов отдельный пароль: при входе по паролю GAL сверяет его с API LTHub (`POST /api/auth/login`) и, если LTHub подтвердил, делает этот пароль паролем аккаунта в GAL. Поэтому один и тот же пароль работает в обоих сервисах, а смена пароля в LTHub автоматически действует в GAL. Если LTHub недоступен — GAL пускает по последней подтверждённой копии пароля (или по кнопке «Войти через LTHub»). Логин LTHub хранится в `external_identities.lthub_login` (миграция `033_lthub_password.sql`); после подтверждения пароля OAuth-вход его больше не перевыпускает.

## GAL как OAuth-провайдер

GAL одновременно работает OAuth 2.0 provider для LTHub: LTHub регистрирует и логинит пользователей через GAL (кнопки «Зарегистрироваться через GAL» / «Войти через GAL»).

- `GET /oauth/authorize` — consent-страница; анонимного пользователя ведёт на `/auth/login?next=...` и возвращает к подтверждению после входа.
- `POST /oauth/authorize` — `allow`/`deny`; выдаёт одноразовый код (TTL 5 минут, в БД только SHA-256-хеш).
- `POST /oauth/token` — `authorization_code` + PKCE S256, проверка `client_id`/`redirect_uri`/`code_verifier`, одноразовость; opaque access token на 30 дней (тоже хеш в БД).
- `GET /oauth/userinfo` — `sub`, `preferred_username`, `login`, `name`, `display_name`, `avatar_url`.
- `GET /.well-known/oauth-authorization-server` — metadata.
- Клиенты задаются статическим реестром в `app/services/oauth_provider.py` (таблицы `oauth_clients` нет); LTHub — публичный клиент без `client_secret`. Доступ к таблицам OAuth — только `service_role` (миграция `021_oauth_provider.sql`).

**Важно:** миграция `021_oauth_provider.sql` применена к проду 2026-11-17; кнопки в LTHub могут быть включены.

## Bradley–Terry

Глобальная сложность считается моделью Bradley–Terry по попарным сравнениям из личных шкал; погрешность и 95% ДИ оцениваются кластерным бутстрэпом по пользователям. Подробности и математика — [docs/bradley_terry.md](docs/bradley_terry.md). Пересчёт выполняется автоматически после оценок/модерации; вручную:

```bash
python scripts/recompute_bt.py          # нужны URL и service role key
python scripts/bt_experiment.py         # синтетический эксперимент точности/устойчивости
```

## Топ-5

Заявка подаётся вместе с прохождением: чекбокс «Заявка в топ-5» в форме доказательства открывает поля «запрашиваемое место» (1–5) и «обоснование сложности». Заявки видны модераторам в общей очереди `/moderation` с тремя решениями: «Принять как сложное» (модератор выбирает место 1–6, по умолчанию — запрошенное), «Принять» и «Отказать». `/top5` — свои заявки и их карточки; независимая экспертиза временно отключена. Одобренная заявка добавляет временную силу поверх постоянного BT-топа — середину между силами соседей выбранного места: достижение видно в общем рейтинге как `#3*`, может занимать слот топ-5 и сдвигать других, но постоянные места не переписывает. На третьей независимой обычной оценке временная запись снимается, BT и место пересчитываются, `*` исчезает. Постоянный алгоритм Bradley–Terry не изменён; детали — [docs/bradley_terry.md](docs/bradley_terry.md). Заявка в топ-5 и прохождение регистрируются разными отпечатками (типы `top5` и `completion`), поэтому одна форма не блокирует сама себя.

## Защита от идентичных заявок (v1.15)

- БД хранит реестр `submission_fingerprints`: отпечаток нормализованного содержимого с типом заявки (`achievement`, `completion`, `top5`, `report`) и submitter_id. Точный повтор блокируется уникальным ключом в БД, а не проверкой в UI; похожие, но не идентичные заявки не определяются.
- Прохождение отправляется одним атомарным service-role RPC `submit_completion_with_proofs`: файлы загружаются заранее, байтовый SHA-256 считает backend, ссылки канонизирует БД. В одной транзакции меняется заявка, заменяются proofs и регистрируется попытка; при дубликате прежние proofs возвращаются откатом.
- Повтор отклонённой заявки возможен только с изменёнными параметрами или доказательствами; счётчик `submission_attempt` хранит номер попытки, отпечаток сохраняется после отклонения/отмены. Одинаковое доказательство нельзя приложить дважды к одному прохождению.
- Миграция `036_submission_fingerprints.sql` подготовлена, но **к проде не применена** — требуется решение владельца. После применения запускается `python scripts/backfill_proof_hashes.py`. До применения работает legacy-путь; без service-ключа отправка прохождения недоступна. Подробности — [docs/README.md](docs/README.md).

## База данных

Миграции лежат в `migrations/` и применяются **по порядку**:

- `001_init.sql` — схема, enum-типы, категории, триггеры;
- `002_rls.sql` — Row Level Security, гранты, helper-функции;
- `003_fix_handle_new_user.sql` — `handle_new_user` как `security definer`;
- `004_storage_proofs.sql` — приватный bucket `proofs` и политики Storage;
- `005_evaluation_rpc.sql` — движок оценок;
- `006_fix_evaluation_rpc.sql` — фикс неоднозначности OUT-параметров;
- `007_player_leaderboard.sql` — агрегат очков игроков;
- `008_hardening.sql` — хардинг RPC и служебных колонок;
- `009_retry_completion_rpc.sql` — повтор/очистка отклонённой заявки;
- `010_ranking_integrity.sql` — гранты, guard-триггер, внутренний пересчёт рангов;
- `011_evaluation_lock.sql` — блокировка оценок после перехода в `ranked`;
- `012_revoke_internal_execute.sql` — запрет вызова внутренней функции пересчёта;
- `013_ui_features_and_hardening.sql` — soft-delete своих pending, приватность proofs, история модерации, инвариант proof создателя, постраничный лидерборд.
- `014_bradley_terry.sql` — BT-колонки, guard, ранжирование по силе Bradley–Terry, RPC `apply_bt_ratings`.
- `015_external_identities.sql` — привязка LTHub-identity к профилю (только `service_role`);
- `016_completion_review_visibility.sql` — автор видит причину отклонения своей заявки;
- `017_completion_difficulty.sql` — сложность, указанная при создании/прохождении, и её автоприменение после approve;
- `018_auto_first_evaluation.sql` — первая подтверждённая заявка автоматически становится якорем личной шкалы + backfill;
- `019_live_evaluations.sql` — новые оценки принимаются и после выхода в рейтинг; топ пересчитывается, lock снят.
- `020_creation_requires_evaluation.sql` — создание достижения требует предварительной оценки опубликованного;
- `021_oauth_provider.sql` — GAL как OAuth-провайдер (одноразовые коды и токены, PKCE, SHA-256-хеши);
- `022_restore_ranking_and_proof_scheme.sql` — восстановление канонического пересчёта рангов и оценок, защита ссылок-доказательств;
- `023_public_completions.sql` — публичные RPC-списки прошедших достижение и пройденных игроком достижений (без email/pending).
- `024_backfill_ranked_threshold.sql` — перевод в `ranked` достижений, уже набравших 2 оценки до снижения порога, и пересчёт рангов.
- `025_bt_uncertainty.sql` — SE и 95% ДИ BT-рейтинга: новые колонки, guard, расширенный RPC `apply_bt_ratings`.
- `026_public_completion_proofs.sql` — доказательства в публичных списках прохождений: RPC возвращают proofs для approved-выполнений опубликованных достижений.
- `027_top5_temporary_rating.sql` — предварительный топ-5: заявки, журнал решений, временные силы, общая вьюха рейтинга с `permanent_rank`/`display_rank`. Таблицы экспертных приглашений остались в схеме, но приложение их не использует.
- `028_proof_visibility.sql` — флаг `achievement_completions.proofs_visible` (по умолчанию `true`, доказательства видимы): скрытие доказательств прохождения, запрет скрытия для верификации создателя, фильтрация proofs в публичных RPC для всех, кроме владельца и модераторов.
- `029_submit_evaluation_position_clamp.sql` — позиция оценки зажимается по числу других оценок пользователя (без «дыр» в нумерации). Применена к проду 2026-11-17.
- `030_top5_apply_upsert.sql` — адресный upsert временных сил вместо очистки всего кэша. Применена к проду 2026-11-17.
- `031_top5_completion_claims.sql` — заявка в топ-5 вместе с прохождением: `completion_id`, необязательный `evidence_url`, guard/RLS для автора или владельца прохождения, backfill старых заявок. Применена к проду 2026-11-17.
- `032_content_refactor.sql` — контент-рефактор: русские названия категорий (slug сохранены), новые категории «Творчество»/«Спорт и здоровье»/«Дом и быт», формализованные тексты достижений. Применена к проду 2026-11-17.
- `033_lthub_password.sql` — `external_identities.lthub_login` (логин в LTHub для проверки пароля) и `password_synced` (подтверждённый пользователем пароль не перевыпускается при OAuth-входе). Применена к проду 2026-11-23.
- `034_creator_top5_claim.sql` — заявка в топ-5 при создании достижения.
- `035_completion_comment.sql` — комментарий к заявке на прохождение (`achievement_completions.comment`), RPC `set_completion_comment` и `remove_completion_proofs`, публичные RPC прошедших пересозданы с колонкой `comment`. **Применена к проду 2026-11-24.**
- `036_submission_fingerprints.sql` — технический запрет идентичных заявок (D25): `submission_attempt`, `proofs.content_hash`, реестр `submission_fingerprints`, service-role RPC `submit_completion_with_proofs`, backfill и отзыв прямых INSERT у клиентских ролей. **К проде не применяется: требуется решение владельца; перед применением — `scripts/backfill_proof_hashes.py`.**

Применение:

```bash
python scripts/apply_migrations.py            # все миграции по порядку
python scripts/apply_migrations.py 015        # только 015 (префикс номера)
python scripts/apply_migrations.py migrations/015_external_identities.sql
python scripts/backfill_proof_hashes.py   # после 036: SHA-256 старых файлов + пересчёт отпечатков
```

Скрипт использует Supabase Management API (`SUPABASE_ACCESS_TOKEN`) и последовательно выполняет SQL. Повторное применение `001` на существующей БД ожидаемо упадёт на `create type` — для существующего проекта применяйте только новые файлы.

## Прод

1. Регистрация → создание достижения → proof → модерация → публикация.
2. Выполнение → proof (SHA-256, атомарная отправка через service role) → дубликат отклоняется БД → модерация → оценка → глобальный рейтинг → очки → player leaderboard.
3. Жалоба → очередь модератора → принятие (скрытие достижения) или отклонение.
