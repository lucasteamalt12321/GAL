# Project Brief — Global Achievement List (GAL)

## Цель

Глобальная платформа для рейтинга человеческих достижений. Сравнение достижений из разных сфер (Geometry Dash, музыка, шахматы, программирование, Minecraft, образование, спорт) через единую относительную шкалу сложности, построенную на личных сравнениях пользователей.

> **Статус: MVP v1.0–v1.11 завершены и задеплоены.** Все миграции 001–032 применены к проду (025/026/027 — 2026-11-14, 028 — 2026-11-15, 021/029/030/031/032 — 2026-11-17). Вход через LTHub и GAL как OAuth-провайдер, «Мои заявки», сложность при создании/прохождении, сравнительный выбор и живые оценки (новые заявки меняют топ). Предварительный топ-5: временная позиция `#N*` в общем топе с переходом на третьей обычной оценке; постоянный BT-алгоритм не изменён. С 2026-11-17 независимая экспертиза топ-5 отключена. v1.10 добавляет видимость доказательств: при отправке прохождения доказательство можно скрыть от других; публичные списки не показывают его, владелец и модераторы видят, верификацию создателя скрыть нельзя (миграция 028 применена к проду 2026-11-15; по умолчанию доказательства видимы). **v1.11 (D18, 2026-11-17): заявка в топ-5 подаётся чекбоксом вместе с прохождением (место 1–5 + обоснование сложности), модератор рассматривает её в общей очереди тремя решениями («принять как сложное» со своим местом 1–6, «принять», «отказать»), временная сила — midpoint между соседями выбранного места; маршрут `/top5/apply` удалён, миграция 031 применена к проду 2026-11-17 (HTTP 201, live-проверка guard/RLS в откатываемой транзакции пройдена).** UI оформлен в стиле VKUI (light/dark), ошибки Storage показываются пользователю понятным текстом. Создать своё достижение можно только после оценки опубликованного достижения (проверка в UI, сервисе и RLS). Публичные профили показывают очки, пройденные и созданные достижения; карточка достижения — место, BT-силу с ± SE и 95% ДИ, прошедших пользователей и отправку прохождения. Security: CSP/nosniff/HSTS, фильтрация схем ссылок, устойчивость сессии к сетевым сбоям. 2026-11-15 проведён сквозной баг-хант (D17): исправлены фоновый auto-refresh токенов, распознавание невалидной сессии, регистрация служебных email, Host-доверие в recover, не-ASCII state LTHub, wildcard в логине, смена пароля без обновления сессии, дробный `rank_order` в сортировках, фильтр постоянных мест в профиле, гонка очистки временного топа (миграция 030) и «дыра» в позиции оценки (миграция 029); контент/модерация проверены без новых находок. `pytest` — 337 passed, `ruff check`/`format` — чисто.

## Рамки v1.11 (D18) — заявка в топ-5 при прохождении

- чекбокс «Заявка в топ-5» в форме доказательства прохождения (любой пользователь): поля «запрашиваемое место» 1–5 и «обоснование сложности»; доказательство — proof самого прохождения, отдельная ссылка не нужна;
- доступность: достижение опубликовано, <3 обычных оценок, не занимает постоянное место в топ-5, нет активной заявки; одна активная заявка на достижение;
- заявка привязана к прохождению (`top5_applications.completion_id`, миграция 031); guard/RLS разрешают подачу автору достижения или владельцу прохождения;
- заявки с топ-5 — в общей очереди модерации: бейдж запрошенного места, обоснование, селект места модератора 1–6 (по умолчанию запрошенное) и три решения: «Принять как сложное» (`approved_top5`), «Принять» (`approved`, заявка отклоняется), «Отказать» (`rejected`); прохождение и заявка закрываются одним решением;
- запрет самоодобрения места модератором; если третья оценка уже конвертировала заявку, закрытие пропускается; сбой закрытия заявки — предупреждение, решение по прохождению сохраняется;
- временная сила — midpoint между `bt_strength` соседей выбранного места в рабочем списке (постоянный ranked-топ + ранее одобренные временные в порядке решений); края экстраполируются (`TOP5_MIN_GAP=0.05`, `TOP5_EDGE_GAP=0.5`); `anchored_strength` и смешивание удалены;
- отдельный маршрут подачи `/top5/apply` удалён; старая секция очереди топ-5 остаётся только для legacy-заявок без `completion_id`;
- совместимость до миграции 031: `PGRST204` по `completion_id` мягко деградирует (заявки не привязываются, очередь по-старому);
- экспертиза не добавляется (остаётся отключённой с 2026-11-17).

## Рамки v1.10 (D16) — видимость доказательств

- при отправке прохождения автор выбирает, показывать ли доказательство другим пользователям;
- скрытое доказательство не выводится в карточке достижения и публичном профиле (пустой список proofs в RPC);
- владелец прохождения и модераторы видят скрытые доказательства (проверка `auth.uid()`/`is_moderator()` в RPC, очередь модерации — напрямую под RLS);
- верификация создателя (прохождение собственного достижения) скрыта быть не может — триггер БД принудительно ставит `proofs_visible = true`;
- миграция 028 и обратная совместимость: до её применения код сохраняет доказательства видимыми и не ломает отправку.

- независимая экспертиза временно отключена (2026-11-17): приглашения и отдельные голоса недоступны в UI и сервисе, legacy-голоса `expert` не учитываются; таблицы экспертных приглашений остаются в схеме 027 для совместимости;

## Рамки v1.2 (D13) — Bradley–Terry

- построение попарных сравнений из индивидуальных шкал (все пары, вес `1/(k-1)`);
- оценка глобальных сил регуляризованным MM-алгоритмом (prior κ=0.5, центрирование);
- колонки `bt_strength`, `bt_rating` (1000 + 400·s/ln10), `bt_comparisons`, `bt_updated_at`;
- ранжирование по `bt_strength desc` с fallback на среднюю позицию;
- атомарное применение через RPC `apply_bt_ratings(jsonb)` (service role) + advisory lock;
- автопересчёт после оценок, модерации и принятия жалоб; ручной `scripts/recompute_bt.py`;
- эксперимент точности/устойчивости (`scripts/bt_experiment.py`) и docs/bradley_terry.md.

## Рамки v1.8 (D14) — надёжность Bradley–Terry

- кластерный nonparametric bootstrap по личным шкалам пользователей (минимум 3 шкалы, 5 валидных реплик);
- SE и 95% percentile CI для BT-рейтинга с детерминированным seed и адаптивным числом реплик;
- хранение `bt_rating_se`, `bt_rating_ci_low`, `bt_rating_ci_high` (миграция 025) и защита полей guard-триггером;
- вывод «± SE» и доверительного интервала в карточке достижения и лидерборде; при недостатке данных интервал скрывается;
- тесты стабильности, краевых случаев и SQL/payload-контракта; документация методики и ограничений.

## Рамки MVP (v1.0)

Стек: Python + FastAPI + Jinja2 + Supabase (PostgreSQL + Auth + Storage) + Vercel.

MVP покрывает базовую цепочку:

```text
Achievement → Proof → Moderation → Evaluation → Global Rank → Player Score → Leaderboard
```

## Что НЕ входит в MVP

- AI-модерация;
- weighted average / опыт пользователя;
- reputation score;
- исторический график рейтинга;
- автоматическое определение дубликатов;
- социальная сеть / чаты;
- внутренние достижения сайта;
- интеграция API игр;
- мобильное приложение;
- статус Draft (только `pending → published`).

## Draft Decision (Draft отсутствует)

- User создаёт `pending` achievement
- Creator обязан приложить proof собственного выполнения
- Achievement публикуется только после модерации
- Creator автоматически становится первым выполнившим и первым evaluater-ом

## Success Criteria MVP

Пользователь способен полностью пройти цикл: регистрация → создание достижения → proof → модерация → публикация → выполнение другим пользователем → proof → модерация → личная оценка → попарные сравнения → глобальная сила Bradley–Terry → ранг → очки → player leaderboard.
